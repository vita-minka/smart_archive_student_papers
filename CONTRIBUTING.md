# Совместная работа над ThesisHub

## Порядок SDD

Перед реализацией согласовать ожидаемое поведение и способ проверки в соответствующей спецификации. При изменении API обновлять контракт и затронутые компоненты. Исправление реализации под уже принятую спецификацию не требует переписывать все документы.

**Задача → временная ветка → спецификация → реализация → проверки → Pull Request → review коллегой → merge в `main`.**

## Ветки

Постоянная ветка — `main`. Для отдельных задач создаются короткоживущие ветки:

- `docs/product-scenarios` — документация;
- `feat/bm25-index` — функциональность;
- `fix/prototype-navigation` — исправление.

Постоянные ветки по именам участников и обязательная `develop` не требуются.

## Команды для работы

Адрес общего репозитория: `https://github.com/vita-minka/smart_archive_student_papers`.

```bash
git clone https://github.com/vita-minka/smart_archive_student_papers.git
cd smart_archive_student_papers
git switch main
git pull --ff-only
git switch -c docs/update-product
```

После изменений:

```bash
git status
git diff
git diff --check
git add README.md spec/product/product.md
git commit -m "docs: update product description"
git push -u origin HEAD
```

Затем открыть Pull Request в `main`, описать изменения, выполненные проверки и ограничения. Запросить review другого участника; после принятия удалить временную ветку.

## Распределение ответственности

- **Эльсон Элина:** `frontend/`, `prototype/`, `spec/product/`.
- **Воложенкова Виктория:** `search/`, `corpus/`, `benchmark/`, документация BM25/RAG.
- **Корольков Игорь:** `backend/`, `infra/`, архитектура, API и модель данных.

Общие изменения и интеграционные контракты согласуются между всеми участниками. Ответственный за каталог не является единственным, кто может его изменять.

## Review

Проверяющий оценивает соответствие спецификации, читаемость, корректность ссылок, отсутствие секретов и фактические проверки. Автор устраняет замечания. Собственное подтверждение PR не заменяет review коллеги.

В private-репозитории техническая защита ветки может зависеть от настроек GitHub; даже если она недоступна, команда придерживается правила PR и review.

## Готовность изменения

- Спецификация и реализация согласованы.
- Изменение проверено доступным способом.
- Не сломаны связанные API и страницы.
- README и документация обновлены при изменении поведения.
- В PR явно указано, что ещё не реализовано.
- Результаты benchmark, тестов и реальных запусков не выдумываются.

Не публиковать закрытые студенческие работы, персональные данные, ключи API и другие секреты.
