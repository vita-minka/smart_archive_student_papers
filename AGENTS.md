# AGENTS.md — правила проекта ThesisHub

Этот файл находится в корне репозитория и применяется к трём направлениям: frontend/продукт, поиск/RAG и backend/интеграция. Он предназначен для участников команды и кодинговых агентов.

## 1. Цель и границы проекта

ThesisHub — веб-приложение для хранения, поиска и анализа студенческих и научных работ. Пользователь загружает PDF курсовой, дипломной работы или статьи, задаёт вопрос и получает ответ с проверяемыми ссылками на найденные документы.

- Студент ищет близкие темы и методы; преподаватель сопоставляет направления исследований.
- Система может показывать тематическую близость, но не объявляет работу плагиатом автоматически.
- Источники ответа должны быть прослеживаемы до конкретного документа и, если доступно, страницы.
- На первой контрольной точке представлены документация и автономный прототип. Работающий поиск, сервер и LLM создаются позже.
- Нельзя представлять демонстрационные ответы, вымышленные документы или результаты benchmark как настоящие.

## 2. Архитектура и обязательные ограничения

| Компонент | Планируемое назначение | Ключевое ограничение |
| --- | --- | --- |
| Frontend | Загрузка PDF, поиск, чат, список источников | Не подменять реальные ответы mock-данными без маркировки |
| Backend | API, хранение метаданных, интеграция поиска и LLM | Согласовать контракты с frontend и search |
| Search | Извлечение текста, токенизация, обратный индекс, BM25 | **Индекс BM25 реализуется самостоятельно** |
| Corpus | PDF, текстовые фрагменты, автор, название, год, страницы | Не публиковать чужие работы без разрешения |
| LLM | Ответ по top-K фрагментам с цитированием | Не выдумывать источники и содержание работ |
| Benchmark | 20 вопросов, gold-разметка, Recall@5, MRR, latency | Не менее 3 релевантных документов на вопрос |

Готовые поисковые индексы и готовые реализации BM25 (например, `rank-bm25`, Elasticsearch, OpenSearch или Whoosh) не применяются для выполнения обязательной части НИРС. Библиотеки для токенизации или лемматизации допускаются, если выбор обоснован. Документы и запросы должны проходить согласованную предобработку.

Планируемый путь запроса: браузер → backend → собственный BM25 → backend → LLM → браузер. Выбор конкретных версий, серверов и моделей фиксируется в технической спецификации после согласования командой; не заявлять неподтверждённые ресурсы как имеющиеся.

## 4. Что прочитать перед изменениями

1. Задачу, `README.md`, этот файл и применимые инструкции каталога.
2. `spec/product/product.md` и `spec/product/scenarios.md`.
3. `spec/tech/architecture.md` и контракт затрагиваемого API.
4. Для корпуса и поиска — `spec/tech/rag.md`, `benchmark/README.md` и `spec/tech/testing.md`.
5. Реальный код и тесты: план в Markdown не подтверждает существование реализации.

## 5. Порядок работы (SDD)

1. Сформулировать задачу и критерии готовности.
2. При изменении поведения, архитектуры или API сначала обновить соответствующую спецификацию.
3. Реализовать небольшое законченное изменение, не ломая соседние компоненты.
4. Проверить результат тестами или воспроизводимой ручной проверкой.
5. Обновить инструкции запуска и описание ограничений.
6. Оформить Pull Request с перечнем изменений и фактически выполненных проверок.

## 6. Git и совместная работа

- `main` содержит согласованные изменения; работа ведётся в временных ветках `docs/...`, `feat/...` и `fix/...`.
- Изменения попадают в `main` через Pull Request и review другого участника.
- Не делать force-push и не переписывать общую историю без согласования.
- Не включать в Git пароли, токены, персональные данные, защищённые авторским правом PDF без разрешения, локальные индексы и крупные артефакты.
- Не выдумывать результаты метрик, тестов, демонстраций или историю изменений.

## 7. Критерии качества

Поиск должен быть воспроизводим: фиксируются версия корпуса, параметры BM25, способ предобработки, список релевантных документов и ранжированная выдача. Для 20 вопросов рассчитываются Recall@5 и MRR; отдельно измеряется время ответа. При отсутствии релевантных источников система не должна выдавать уверенный неподтверждённый ответ.

Если описание и код расходятся, исправить расхождение и явно указать, что фактически реализовано.
