# Команда и зоны ответственности

Команда ThesisHub состоит из трёх участников. Обязанности распределены по основным компонентам проекта, а интеграция, проверка и защита выполняются совместно.

| Участник | Роль проекта | Основная работа | Результат к контрольной точке 1 |
| --- | --- | --- | --- |
| **Эльсон Элина** | Frontend / продукт | Пользовательские сценарии, требования к интерфейсу, прототип страниц, состояния поиска и источников | Продуктовые спецификации, HTML/CSS/JS-прототип, сценарий демонстрации |
| **Воложенкова Виктория** | Поиск / RAG / benchmark | Подготовка корпуса, формат PDF и метаданных, предобработка, собственный BM25, тестовые запросы и метрики | RAG-спецификация, план корпуса, формат вопросов и оценивания |
| **Корольков Игорь** | Backend / интеграция / DevOps | Архитектура, контракты API, модель данных, взаимодействие компонентов, инфраструктура и CI/CD | Техническая архитектура, проекты API, схема данных, план интеграции |

## Общая ответственность

- Все трое участвуют в выборе корпуса и составлении 20 тестовых вопросов.
- Для каждого вопроса в будущем benchmark размечается не менее трёх релевантных документов.
- Frontend и backend совместно согласуют API загрузки и отображения источников.
- Backend и поиск согласуют формат фрагментов, метаданных и контекста для LLM.
- Каждый участник может объяснить основной путь данных: PDF → BM25 → top-K → LLM → ответ с источниками.
- Pull Request проверяет другой участник команды.

## Рабочие границы

- `frontend/`, `prototype/`, `spec/product/` — Эльсон Элина.
- `search/`, `corpus/`, `benchmark/`, `spec/tech/rag.md`, `spec/tech/search-api.yaml` — Воложенкова Виктория.
- `backend/`, `infra/`, `spec/tech/architecture.md`, `spec/tech/api.yaml`, `spec/tech/data-model.md`, `spec/tech/cicd.md` — Корольков Игорь.
- Корневые документы, `docs/`, `spec/plan.md`, `tests/` — общие задачи по согласованию.

## Порядок работы

1. Согласовать продуктовые сценарии и границы MVP.
2. Утвердить API и формат корпуса, затем распределить задачи в GitHub Issues.
3. Разрабатывать компоненты в отдельных ветках с Pull Request и review.
4. На первой контрольной точке показать документацию и демонстрационный прототип.
5. На следующем этапе реализовать собственный BM25, собрать корпус, провести benchmark и интегрировать веб-приложение.

Роли распределены для планирования работы, а не как утверждение, что перечисленные будущие компоненты уже реализованы.
